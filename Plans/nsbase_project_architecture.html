NsBase architecture plan — core sync strategy and module specs for Booking, Catalog, and Clinic

The problem
You update NsBase (auth, media, email templates, settings…) and you want every project — Booking, Clinic, Catalog — to get those fixes without copy-pasting. Git branching alone won't solve this cleanly. The right answer is composer packages.
Recommended approach — NsBase as a private composer package
How it works
1
NsBase lives in its own repo
It is a standard Laravel package. All core modules (auth, settings, media, activity log, email templates, users/roles) live here. You push updates to this repo.
2
Each project installs NsBase via composer
Booking, Clinic, Catalog each do composer require nassim/nsbase. They get the core. NsBase publishes its migrations, config, and views.
3
Update = one command per project
When you fix a bug in NsBase, push the tag. Then in each project: composer update nassim/nsbase. Done. No copy-paste, no manual merging.
4
Project-specific code stays in the project
Booking logic, clinic appointments, catalog products — none of that is in NsBase. Each project extends the core, never modifies it.

If composer packages feel like too much right now
Simple fallback: use git subtree. NsBase is one repo. Each project adds it as a subtree. When NsBase updates, you pull the subtree. No branches, no copy-paste — just one command per project. Much simpler than submodules.
git subtree pull --prefix=packages/nsbase git@github.com:you/nsbase.git main --squash

Build phases
1
Service + staff setup Phase 1
Services CRUD (from core), Staff CRUD (name, bio, image, assigned services). Admin can assign which staff handles which service.
2
Availability rules Phase 1
Per-staff weekly schedule: Mon–Fri 9am–5pm, break 12–1pm. Stored as rules, not individual slots. Exception dates (holidays, leaves) override rules.
3
Public booking form Phase 1
Blade page: pick service → pick staff (optional) → pick date → pick slot → fill details → submit. Slots generated from availability rules on the fly, not pre-stored. Rate-limited like contact form.
4
Admin booking management Phase 2
Vue table with filters (status, staff, service, date range). Status change with confirmation dialog. Notes field. Email notification on every status change using core email templates.
5
Calendar view Phase 2
Simple week/day grid in Vue. No heavy library needed — pure CSS grid by hour slots. Shows confirmed bookings per staff column. Click to see details.
6
Client portal (optional) Phase 3
Logged-in clients see their own bookings, can cancel, can rebook. Only build this if the client explicitly needs it.

Key design decision — no checkout
Catalog is display only. Client can browse, filter, see product details, and send a quote request. No cart, no payment. If the client later wants checkout, that's a separate scope upgrade or WooCommerce recommendation. Keep this boundary explicit from day one.
Build phases
1
Categories + products CRUD
Vue admin. Category tree (max 2 levels: category → subcategory). Product: name (multilingual), description, price display (optional), images via core media, SEO fields via core trait, is_published toggle.
2
Attributes system
Admin defines attributes (Color, Size, Material…) and their values. Products are tagged with attribute values. Public filter sidebar uses these. Do not over-engineer — a simple pivot table is enough.
3
Public catalog with filter
Blade page with sidebar (categories, attributes, optional brand). Filter via query params — full page reload is fine, no need for Vue SPA here. Pagination. Product card: image, name, short description, price if set.
4
Quote request
Simple form: name, phone, email, product reference (auto-filled from product page), message. Stored in quote_requests table. Admin notified via core email template system.

Build phases
1
Doctors + services CRUD
Doctor profile (name, speciality, bio, image via core media). Assign services to doctors via pivot. Services come from core module.
2
Patients CRUD
Patient record: name, phone, email, date of birth, notes. Separate from users table — patients are not system users by default. Only create a patient user account if portal is needed.
3
Schedule + appointments
Doctor weekly schedule (same availability rules pattern as booking). Receptionist creates appointments: patient → doctor → date → time → service. Status managed by receptionist or doctor.
4
Doctor dashboard
Vue view: today's appointments, upcoming week, status update buttons. Doctor sees only their own. No access to other doctors or admin settings.
5
Public booking page (optional)
Same pattern as Booking module — patient fills form, admin or receptionist confirms. Do not auto-confirm without human review by default.
The golden rule for keeping core clean
Never modify a file that came from NsBase inside a project. If you need to change behaviour, extend via Laravel's service container, event listeners, or config overrides. This is what lets you update NsBase without breaking projects.
What you can safely do in projects
Publish and customise views
php artisan vendor:publish --tag=nsbase-views — copies views to your project. You edit your copy, NsBase update doesn't overwrite it.
Override config
Publish NsBase config, edit it in your project. Controls features, defaults, behaviour without touching core code.
Extend models
Project's User model extends NsBase's BaseUser. Add project-specific relationships and methods there.
Listen to core events
NsBase fires events (UserCreated, BookingStatusChanged…). Projects register listeners in their own EventServiceProvider. Core doesn't know about the listener.
Never edit files in vendor/nassim/nsbase/
They will be overwritten on the next composer update. If you need to change something, override it at the project level or open a fix in the NsBase repo itself.
Versioning NsBase
Use semantic versioning. 1.x = stable, no breaking changes. 2.x = breaking change (migration schema, renamed method). Each project pins to a major version: "nassim/nsbase": "^1.0". This means minor updates auto-install, breaking changes require deliberate upgrade.
